## 1. Project in one paragraph

**AvaLab (آوالب)** is a bilingual (Persian/English) web-based **audio laboratory** for teaching two university courses: **Signals and Systems** and **Multimedia Systems**. A student loads an audio file (or records/generates one), applies signal-processing and compression algorithms, and **sees and hears the effect live**: waveform, spectrogram, Fourier magnitude/phase, sampling and quantization effects, lossless vs lossy compression, quality metrics, convolution/reverb, filters, and AI-model-based tools. Every tool is paired with theory (formulas + short explanation) so the app is both an experiment bench and a teaching aid.

The product must be usable by real students and instructors: it will be deployed on the web for students and for in-class use inside the university. **Both the source code and the deployment are meant to be public, for educational purposes** (open-source educational project). Everything committed MUST therefore be publication-ready. See §14 for the openness rules.

The owner also **demonstrates the project locally on his own machine** (presentation/defense). Therefore the whole stack, including every ML model, MUST run on a normal laptop (CPU-only is the baseline) and MUST work **offline** after a one-time model download. See §8.

Primary goals, in priority order:
1. **Educational correctness** — algorithms and formulas are right, units are right, results are verifiable.
2. **Live interactivity** — change a parameter, see/hear the result with minimal delay.
3. **Clarity** — a student can understand *why* the result looks/sounds like that.
4. **Robustness** — handles arbitrary user files up to 5 minutes without freezing or crashing.

Non-goals: user accounts, social features, payments, a DAW-grade editor, mobile-first design (must be usable on tablet/phone, but desktop is the target).

## 2. Architecture (decisions already made — do not re-litigate)

Monorepo, two runtimes:

```
avalab/
├─ AGENTS.md
├─ docs/
│  ├─ PROGRESS.md          # living status log (agents update every session)
│  ├─ DECISIONS.md         # ADR-style log of any deviation/new decision
│  ├─ MODELS.md            # every ML model: HF id, license, size, task, revision
│  └─ ALGORITHMS.md        # every hand-implemented algorithm: formula, reference, tests
├─ apps/
│  ├─ web/                 # React + TypeScript + Vite SPA
│  └─ api/                 # Python FastAPI backend
├─ packages/
│  └─ dsp/                 # PURE TypeScript DSP library (no DOM, no React)
├─ tools/
│  └─ golden/              # Python scripts generating reference vectors (NumPy/SciPy/librosa)
├─ docker/                 # Dockerfiles + compose
└─ .github or CI config     # lint, typecheck, test (CI provider decided by owner)
```

### Where does each thing run?

| Concern | Runs in | Why |
|---|---|---|
| Decoding of any uploaded format → canonical PCM | **Backend** (ffmpeg) | Browsers cannot decode every format. |
| Waveform, spectrogram, FFT/STFT, Re/Im editing, resampling, quantization, filters, convolution/reverb, speed/reverse, time-stretch, metrics, hand-written compressors | **Browser** (`packages/dsp` inside Web Workers) | Live feedback, no server round-trip, scales with students for free. |
| Real codecs: MP3, AAC, Opus, Vorbis, FLAC (and WAV/PCM baseline) | **Backend** (ffmpeg) | Real encoders; we do NOT reimplement them. |
| ML models (HuggingFace): separation, denoising, super-resolution, neural codecs, ASR, pitch/beat, classification | **Backend** (PyTorch / transformers) | Heavy; GPU optional. |
| Reference/golden vectors for tests | `tools/golden` (Python) | Independent ground truth for our TS code. |

Rule of thumb: **if it must react while a slider moves → browser; if it needs a real codec or a neural network → backend.**

### Hand-implement vs. use a library

The owner decided: implement ourselves **only the special, educationally valuable algorithms**; use ready-made tools for everything else.

**MUST implement ourselves (in `packages/dsp`, TypeScript, with tests against golden vectors):**
- DFT (naive O(N²), for teaching) and FFT (iterative radix-2 Cooley–Tukey + a Bluestein/zero-pad strategy for non-power-of-2), inverse FFT, real-FFT optimization
- STFT / inverse STFT with window functions (rectangular, Hann, Hamming, Blackman, Kaiser) and overlap-add
- Linear convolution (direct) and fast convolution (FFT-based, overlap-add) — used for reverb and filters
- Resampling (with and without anti-aliasing filter: windowed-sinc low-pass), decimation/interpolation
- Quantization (uniform, with optional TPDF dither), bit-depth reduction, quantization-noise measurement
- μ-law / A-law companding
- Lossless toy codecs: RLE, Huffman (canonical), delta/first-order predictor + Huffman (FLAC-like idea), entropy calculation
- A simple **lossy transform codec**: MDCT (windowed, TDAC) + uniform quantization + Huffman — to demonstrate how MP3/AAC-like codecs work, with an adjustable "bit budget"/quantizer step and an optional simple psychoacoustic masking model
- Phase-vocoder time-stretch and pitch-shift (to contrast with plain resampling speed change)
- Filter design: FIR window method, biquad/IIR (Butterworth, Chebyshev I, RBJ biquads), frequency/phase/group-delay response, pole-zero computation
- Metrics: MSE, SNR, segmental SNR, PSNR (with documented peak definition), compression ratio, bitrate, Shannon entropy
- Fourier-series reconstruction & Gibbs demo, signal generators (sine, square, sawtooth, triangle, noise white/pink, chirp, impulse, step)
- Signal-extent tools: time shift, time scale, time reversal, truncation, zero-padding, energy/power computation

**MUST use existing libraries/models (do NOT hand-write):**
- Audio decoding/encoding for MP3/AAC/Opus/Vorbis/FLAC → **ffmpeg** (via subprocess on the backend)
- Source separation, denoising, super-resolution, neural codecs, ASR, pitch/beat tracking, classification → **HuggingFace / PyTorch models** (see §8)
- Plotting of analytical charts → charting library (see §3)
- Reference values for tests → NumPy / SciPy / librosa in `tools/golden`

If you believe something outside these lists should be hand-written or library-based, write it in `docs/DECISIONS.md` and ask the owner.

## 3. Tech stack (fixed)

- Package manager: **pnpm** workspaces

**Backend (`apps/api`)**
- Python 3.12 (verify PyTorch wheel support; fall back to 3.11 if needed and record it)

- Audio: ffmpeg (system binary), soundfile, NumPy, SciPy, librosa
- ML: PyTorch, torchaudio, `transformers`, plus model-specific packages (e.g. `demucs`) as needed
- Jobs: in-process async job manager with a bounded worker pool (no Redis/Celery). Progress via **Server-Sent Events**
- Tests: pytest; lint: ruff; types: mypy (or pyright) on `apps/api`

**Deployment**
- Docker Compose: `web` (static build behind nginx/caddy) + `api`. CPU by default; GPU profile optional.
- No database. Temporary files on disk with TTL (see §7).

## 4. Product requirements → feature catalogue

Every feature has an ID. Reference IDs in commits, PRs, and `docs/PROGRESS.md`. Priorities: **P0** = MVP (must exist for a usable product), **P1** = core, **P2** = planned, **P3** = stretch.

### F01 — Audio input (P0)
- Upload any audio format (anything ffmpeg can decode), max **5 minutes (300 s)** and a max file size (default 100 MB, configurable). Reject longer files with a clear bilingual error — never silently truncate.
- Backend `ingest` normalizes to canonical **float32 PCM WAV**, keeps original sample rate (cap at 96 kHz; resample above that and tell the user), keeps channel count (max 2; downmix >2).
- Also: microphone recording (MediaRecorder → ingest) and built-in **signal generator** (see F12) so experiments work with no file.
- A small set of bundled demo clips (public domain / self-generated only — see §14).
- Analysis tools operate on a **mono downmix by default**; stereo is preserved for playback.

### F02 — Waveform & Spectrogram (P0)
- Waveform with zoom/pan, playhead, selection (time range). Overview + detail for 5-minute files.
- Spectrogram (STFT): selectable window, window size, hop, FFT size, dB range, linear/log/mel frequency axis, colormap. Axis labels with units (Hz, s, dB).
- "Before vs After" side-by-side or overlay for any processing step (original vs processed).
- Live playhead sync between waveform and spectrogram.

### F03 — Sampling rate & bit depth (P0)
- Resample to any target rate (e.g. 48k → 22.05k, 8k, 4k, 1k…) with a **toggle for the anti-aliasing filter** so students can hear/see **aliasing**. Interactive aliasing demo: a pure sine swept past Nyquist, with the alias frequency shown.
- Bit depth 16 → 1 bit, uniform quantizer; optional **dither** toggle; show quantization error signal, noise floor, and measured SNR vs the theoretical ≈ 6.02·N + 1.76 dB.
- Play and display the **difference/residual** (original − processed) on demand.

### F04 — Compression lab: lossless vs lossy (P0 for lossless basics + one lossy; P1 for the rest)
- **Hand-written** (live, in browser): RLE, Huffman, delta+Huffman, μ-law/A-law, and the **MDCT toy lossy codec** with adjustable quantizer/bit budget. Show internals: histogram, code table/lengths, bits per sample, coefficient sparsity.
- **Real codecs** (backend, ffmpeg): FLAC (lossless), MP3, AAC, Opus, Vorbis with bitrate/quality selection. Return the decoded audio for A/B listening plus size/bitrate stats.
- **Comparison view**: one table + charts comparing selected methods side by side (compression ratio, bitrate, metrics from F05, encode time).
- Lossless methods MUST be verified bit-exact on decode (round-trip test) and the UI shows "bit-exact ✓/✗".

### F05 — Quality metrics (P0)
- **MSE, SNR, segmental SNR, PSNR, compression ratio, bitrate**, Shannon **entropy** (and the theoretical lower bound vs achieved bits/sample).
- PSNR definition for audio MUST be documented in the UI and in `docs/ALGORITHMS.md` (peak = full-scale for the chosen sample format). Alignment: codecs introduce delay — metrics MUST compensate for codec delay/padding (cross-correlation alignment) before comparing; never compare misaligned signals.
- **Rate–distortion plot**: quality metric vs bitrate across codecs/settings.
- Optional (P2): a perceptual metric computed on the backend (e.g. PESQ/ViSQOL/other) — only if license permits; record in `docs/MODELS.md`.

### F06 — Playback control: speed & direction (P0)
- Combobox/presets: 0.25×, 0.5×, 0.75×, 1×, 1.25×, 1.5×, 2×, 3×, 4× + custom value; **reverse**; **forward/backward seek** (±5 s / ±10 s) and play-direction toggle.
- Two speed modes that students can compare:
  1. **Resampling mode** — speed and pitch change together (tape-style).
  2. **Time-stretch mode** — speed changes, pitch preserved (our phase vocoder, F08-related). Also **pitch-shift** with duration preserved.
- Show the spectrogram of the result so the difference is visible.

### F07 — Signal extent in time ("گستردگی سیگنال" = *signal duration/support in time*) (P0)
Owner's clarification: this means the **time-domain length/extent of a signal**. Implement a dedicated "Signal Extent" lab:
- Display duration, number of samples, support (non-zero region), signal **energy** and **average power**; classify as energy/power signal.
- Operations: **truncate** to window length, **zero-pad**, time-shift x(t−t₀), time-scale x(at), time-reversal x(−t).
- Show the effect on the spectrum: **frequency resolution Δf = fs/N**, spectral leakage from truncation, zero-padding = interpolation (not new information), and the **time–bandwidth (uncertainty) trade-off** (shorter in time ⇒ wider in frequency), with the Fourier time-scaling property demonstrated interactively.
- Compare finite-duration vs periodic extension.

### F08 — Fourier transform (P0)
- DFT/FFT of the selected segment or whole file: **magnitude** (linear/dB) and **phase** (wrapped/unwrapped, with magnitude-threshold masking of meaningless phase), plus STFT view.
- Window comparison (rect/Hann/Hamming/Blackman/Kaiser): main-lobe width, side-lobe level, leakage demo.
- Compare **our FFT vs library FFT** (accuracy and speed) in a "Benchmark" panel; also a step-through of Cooley–Tukey butterflies for small N (e.g. N=8) as a teaching view.

### F09 — Real/Imaginary editor (P0)
- Show Re{X[k]}, Im{X[k]}, |X[k]|, ∠X[k]. User can **zero, scale, set, or draw** values on Re, Im, magnitude, or phase for selected bins/bands (brush/range-select/numeric entry), then apply **IFFT** and play the result.
- Toggle **Hermitian symmetry enforcement** (X[N−k] = conj X[k]) so the IFFT stays real; when OFF, show how/why the result becomes complex and what is taken (real part) — this is a teaching moment, label it clearly.
- Presets: zero Im, zero Re, zero phase, constant (linear) phase, random phase, magnitude-only / phase-only reconstruction (classic "which carries more information?" demo).
- Frequency-mask drawing (brick-wall ranges) with visible Gibbs/ringing consequences.

### F10 — Reverse & Reverb (P0)
- **Reverse** (time reversal): note and display what changes in magnitude/phase spectra.
- **Reverb** = convolution with an impulse response (LTI system view): built-in IRs (generated exponential-decay noise at several RT60 values, room/hall/plate-style synthetic IRs, telephone-style band-limited IR), **user-uploaded IR**, wet/dry mix, pre-delay.
- Show the IR, its spectrum, and a **step-by-step convolution visualization** (flip-and-slide) on a short excerpt.
- Fast convolution (FFT, overlap-add) is the default for long IRs; direct convolution available for comparison (with timing).
- Terminology: "Reverse" (معکوس‌سازی زمانی) and "Reverb" (پژواک/طنین) are DIFFERENT; the UI and docs MUST NOT conflate them.

### F11 — Filter design & Z-domain (P1)
- Low-pass / high-pass / band-pass / band-stop / notch; FIR (window method, Kaiser) and IIR (Butterworth, Chebyshev I, biquads).
- Plots: magnitude (dB), phase, group delay, impulse response, step response, **pole-zero plot** with the unit circle; stability indicator.
- Apply to loaded audio with live preview; compare filtered spectrogram.

### F12 — Signal generator & Fourier series (P1; the generator itself is needed by P0 demos)
- Sine, square, sawtooth, triangle, impulse, step, white/pink noise, chirp (linear/log), two-tone, AM/FM.
- **Fourier-series reconstruction**: add harmonics one by one with a slider; Gibbs phenomenon on the square wave.

### F13 — Psychoacoustics (P2)
- Simple frequency-masking model (spreading function over critical/Bark bands) visualized over the spectrum, linked to the MDCT toy codec's bit allocation ("what the codec may throw away and why").
- Absolute threshold of hearing curve overlay.

### F14 — AI tools via HuggingFace (P1 → P2; see §8)
- Source separation (vocals/drums/bass/other), denoising, **audio super-resolution** (restoring bandwidth lost by downsampling — pairs with F03), **neural codec** (compare with F04 traditional codecs on the rate–distortion plot), **ASR (Whisper)** with WER vs compression level, pitch/F0 tracking, beat tracking, audio classification.
- All run on the backend as jobs with progress and cancel.

### F15 — Pipeline builder (P3)
- Chain blocks (Resample → Filter → Quantize → Compress → Reverb …) as a node graph or ordered list; per-stage waveform/spectrogram/metrics; save/load as JSON.

### F16 — Education layer (P0 skeleton, P1 content)
- Each tool has a collapsible **Theory panel**: key formulas (KaTeX), 1–2 paragraphs, "what to observe" bullets, common pitfalls.
- **Guided experiments** (lab-sheet style): 5–8 short step-by-step tasks with expected observations (e.g. "Downsample to 8 kHz with the anti-alias filter OFF and describe what you hear").
- **Share by URL**: tool + parameters + demo-clip id encoded in the URL so an instructor can send a ready experiment. (User-uploaded audio is never stored in the URL.)
- **Export**: processed audio (WAV), chart images (PNG), and a one-click **PDF/HTML lab report** with the parameters and metrics used.

### F17 — Internationalization (P0, cross-cutting)
- `fa` and `en`; Persian is the default; full **RTL** layout. See §6.

### F18 — Quality-of-life (P1)
- A/B listening with instant, gapless switching between original and processed at the same playhead position (loudness-matched option).
- Keyboard shortcuts, persistent last-used settings (localStorage, per-viewer only), light/dark theme, responsive layout.

## 7. Backend rules

- **API versioned** under `/api/v1`. Endpoints (minimum; refine via OpenAPI):
  - `POST /ingest` → upload file → `{audio_id, duration_s, sample_rate, channels, ...}`
  - `GET /audio/{audio_id}` → canonical WAV (supports HTTP Range)
  - `POST /codec/encode` `{audio_id, codec, params}` → `{result_audio_id, size_bytes, bitrate_kbps, encode_ms, codec_delay_samples}`
  - `POST /ml/{task}` `{audio_id, params}` → `{job_id}`; `GET /jobs/{job_id}/events` (SSE progress); `DELETE /jobs/{job_id}` cancels
  - `GET /health`, `GET /models` (available models + status)
- **Uploads are untrusted.** Validate by probing with ffprobe (not by extension/MIME), enforce size/duration/channel/sample-rate limits **before** heavy work, run ffmpeg with fixed argument arrays (**never shell string interpolation**), timeouts, and resource limits. Sanitize filenames; store under server-generated UUIDs only.
- **Privacy**: no accounts, no analytics that identify users, no logging of audio content or filenames. Files auto-delete after a TTL (default 60 min; configurable) and on explicit user "delete" action. State this in the UI.
- **Rate limiting** and a global concurrency cap on ML jobs (queue with position feedback). CPU-only deployment MUST work (slower), and the UI must show an honest ETA/progress.
- ML models are **lazy-loaded**, cached in a volume, and loaded once per process. Never download weights at request time without a cache; never block the event loop (run in worker threads/processes).
- Every endpoint has typed request/response models, error responses with stable machine-readable codes + bilingual-ready messages (the frontend translates by code).
- CORS: restrictive, configured via env. Config via environment variables (`pydantic-settings`), `.env.example` committed, real `.env` never committed.

## 8. AI/ML model rules (HuggingFace)

The instructors permit use of pre-trained models. **We never train models.**

- **Never invent a model ID.** Before using any model, verify the HuggingFace repo exists, read its model card, and record in `docs/MODELS.md`: task, HF id, pinned **revision/commit**, size, license (code AND weights), expected CPU/GPU speed, input sample rate/format, known limitations.
- **Licenses matter** (public educational deployment): non-commercial licenses are acceptable only for non-profit educational use — flag any such model in `docs/MODELS.md` (e.g. some neural-codec weights are non-commercial; verify, don't assume). Do NOT use models whose license forbids this use.
- **Lightweight-first rule (local presentation, CPU laptop):** prefer the smallest model that demonstrates the concept. Budget: each model ≤ ~400 MB on disk, all models together ≤ ~2 GB. Do NOT use multi-GB models (e.g. latent-diffusion super-resolution like AudioSR, large Whisper sizes) — a heavier model needs the owner's explicit approval.
- **Offline-first:** provide `scripts/download_models.py` that pre-fetches all pinned models into the local cache; after that the app MUST run with `HF_HUB_OFFLINE=1`. For bundled demo clips, ML results MAY be pre-computed and cached so the live demo never waits on a slow CPU job (the UI labels them "pre-computed").
- **Excerpt limit for slow models on CPU:** source separation and similar jobs default to a ≤ 30–60 s excerpt with a clear "process whole file" option and an honest ETA.
- **Shortlist (searched on 2026-10-19; agents MUST re-verify existence, license, size and pin a revision in `docs/MODELS.md` before use — if a repo moved or changed license, stop and ask):**
  - ASR (F14): `openai/whisper-tiny` (≈39M params, ≈151 MB) and `openai/whisper-base` (≈74M, ≈290 MB); third-party model cards state Apache-2.0 for them — confirm on the official cards. Default to tiny/base. Tiny/base are weak for Persian — use English demo clips for the "WER vs compression" experiment, and offer `whisper-small` as an optional download for Persian.
  - Neural codec (F04/F05): `facebook/encodec_24khz` (small; its HF card showed no license field while the 48 kHz card does, so check `facebook/encodec_48khz` and the upstream `facebookresearch/encodec` repo and record the exact license of the weights) and Descript Audio Codec (DAC; cards state MIT, weights for 16/24/44.1 kHz; one 24 kHz conversion is ≈287 MB, so prefer the 16/24 kHz variants).
  - Denoising (F14): **DeepFilterNet3** (≈2.1M params, ≈8–16 MB, MIT/Apache-2.0; 48 kHz, speech). ONNX exports exist on HF (e.g. `kimtos-labs/denoiser-dfn3`, `TigreGotico/audiosronnx-deepfilternet`); alternatively the upstream `deepfilternet` package. UI note: denoising can *hurt* ASR accuracy — a good teaching point.
  - Bandwidth extension / super-resolution (F14, pairs with F03): small speech-focused ONNX models via the `audiosronnx` package (LavaSR, NovaSR — Apache-2.0 weights; Sidon is CC-BY-NC, avoid unless approved). It is an alpha third-party package: wrap it, pin the version, keep a fallback. These are speech models — use speech demo clips.
  - Source separation (F14): HT-Demucs family (MIT). ONNX/PyTorch repackages exist on HF (e.g. `StemSplitio/htdemucs-*`, ≈250–320 MB per model; the fine-tuned 4-model "bag" is larger and slower). Prefer the **single `htdemucs` 4-stem model**. CPU is slow → apply the excerpt limit above.
  - Pitch/F0 and beat tracking: **no neural model** — use `librosa.pyin` and `librosa.beat.beat_track` (zero extra weights).
  - Audio classification: **lowest priority (P3)**. `MIT/ast-finetuned-audioset-10-10-0.4593` exists but is comparatively heavy — verify size/license; skip unless time remains.
- Models MUST be wrapped behind a small internal interface (`apps/api/avalab_api/ml/<task>.py`) so they can be swapped without touching routes or the frontend.
- Respect each model's required sample rate: resample explicitly, then map results back to the user's rate, and tell the UI what happened.
- Small models that run fine in the browser (e.g. via Transformers.js/ONNX Runtime Web) MAY be added later as an optimization; the backend remains the default.
- AI output is shown with an honest caption ("AI-generated approximation"), especially for super-resolution and denoising, so students don't confuse it with a mathematically exact operation.

## 9. Performance & robustness budgets

- **Main thread MUST NOT run DSP.** All transforms/filters/codecs run in Web Workers or AudioWorklets. A DSP call that can take > 16 ms is a bug on the main thread.
- Supported input: up to **300 s**, up to 96 kHz, mono/stereo. Memory budget: avoid copying large buffers; use transferable `ArrayBuffer`s; process per-channel/mono for analysis; cap simultaneously held full-length buffers and release them.
- Targets (mid-range laptop, 5-min 44.1 kHz mono file): first waveform overview < 1 s after decode; spectrogram overview < 3 s (progressive rendering is OK); parameter change → updated audio/preview for 10–30 s excerpts < 300 ms where mathematically possible. For full-length processing show progress and support cancel.
- Live preview strategy: apply live tools to the **selected/visible excerpt** (default ≤ 30 s) for instant feedback, with an explicit "Apply to whole file" action.
- Every long operation: progress, cancel, and error states. No spinner without an exit.
- Graceful failure: corrupted file, unsupported codec, backend offline → clear bilingual message and recovery path. The frontend MUST remain functional for all browser-side tools when the backend is unreachable (backend-only features are disabled with an explanation).
- Accessibility: keyboard-operable controls, visible focus, ARIA labels (translated), sufficient contrast, `prefers-reduced-motion` respected, spectrogram colormaps selectable incl. a colorblind-safe one; never convey information by color alone.

## 10. State, URLs, and data flow (frontend)

- One global audio session store (Zustand): the **original** buffer (immutable once loaded) plus a processing graph of derived results. Derived results are cached by `(input hash, params)`.
- Tools are **pure functions of (input buffer, params)**. UI components hold no DSP logic.
- Tool parameters are serializable and synced to the URL (excluding user audio) for F16 "Share by URL".
- Sample-rate/time conversions go through shared helpers in `packages/dsp` (`samplesToSeconds`, etc.). **No magic numbers; every quantity carries its unit in its name** (`durationSeconds`, `sampleRateHz`, `cutoffHz`, `gainDb`).

## 11. DSP library rules (`packages/dsp`) — the heart of the project

- **Pure, deterministic, DOM-free** TypeScript. No `window`, `document`, `AudioContext`, React, or I/O. Must run in a Worker, an AudioWorklet, and Node (tests).
- Public function shape: `(input: Float32Array | Float64Array, params: ParamsType) => ResultType` — with explicit result types carrying metadata (e.g. `{samples, sampleRateHz, delaySamples}`). No hidden global state, no mutating inputs.
- Internals use **Float64** for transforms/filters where precision matters; audio buffers at the boundary are Float32. Document it.
- Every algorithm file begins with a header comment: purpose, the **formula(s)**, reference (textbook/paper/standard), complexity, edge cases. Every algorithm has an entry in `docs/ALGORITHMS.md`.
- **Edge cases are mandatory to handle and test**: empty input, length 1, odd lengths, non-power-of-2 FFT sizes, DC signals, full-scale clipping, NaN/Infinity (reject or sanitize explicitly), sample rates at extremes.
- **Correctness verification (non-negotiable):** each algorithm has tests comparing against **golden vectors** produced by `tools/golden` (NumPy/SciPy/librosa) with documented tolerances (e.g. FFT relative error ≤ 1e-9 in Float64, ≤ 1e-5 in Float32 paths). Plus property tests: Parseval's theorem, FFT∘IFFT = identity, convolution theorem, linearity/shift properties, lossless codec bit-exact round-trip, filter stability, energy conservation where applicable.
- Never claim an algorithm "works" without a test that fails when it is wrong.
- Performance-sensitive kernels (FFT, convolution, MDCT) SHOULD be benchmarked; if the budgets in §9 are missed, optimize in TypeScript first (typed arrays, precomputed twiddles, in-place, avoiding allocation in loops). WebAssembly is allowed ONLY after a recorded benchmark proves the need — record in `docs/DECISIONS.md`.
